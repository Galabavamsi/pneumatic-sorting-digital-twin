From a PLC tag to a phone: how the machine data travels

This document covers one thing: how the state of an Allen-Bradley Micro850 controller is read, turned into something a person can use, and delivered to a digital twin and to a dashboard anywhere. It gives the high-level design, the low-level design, a proposal for a compact edge device, and what a client needs in order to use it.

Audience: integrators, plant IT / OT, and anyone deploying this on their own machine

1. High-level design

The system has four tiers. Data flows one way, from the machine outwards. Nothing in the chain can write to the controller, and the plant side only ever opens outbound connections.

2. How the PLC is read

The controller speaks EtherNet/IP, which carries the Common Industrial Protocol (CIP). Reading one variable is a CIP "Read Tag" request addressed by the variable's name. The gateway opens one connection and reuses it for every read.

Tags are read one per request. The protocol also allows several reads to be packed into one frame (the Multiple Service Packet); that is not implemented, and at 26 ms for a full scan it has not been needed.

3. Low-level design

3.1 Gateway components

3.2 Poll loop

  1. If there is no connection, discover the PLC and connect.
  2. If the program is unknown, try each profile's probe tag; the first that answers wins. A fallback profile shows raw I/O for an unknown program.
  3. Read every tag the profile lists. A missing tag becomes "no value"; a failed probe forces re-identification, which is how a program download is noticed.
  4. Derive: step name, fault text, actuator positions, step changes, parts counted, cycle time.
  5. Publish if anything changed, or once a second regardless.

3.3 What the gateway adds

  • Meaning. Step 6 becomes "Upper eject"; fault 9 becomes "Homing did not finish".
  • Actuator position. From the two valve coils. With neither coil on, the last commanded position is kept, because these valves hold their place.
  • Events. A rolling log of step changes, faults, parts and link changes.
  • Cycle time. From the feed step to the part counter increasing.

3.4 Snapshot contract

Every consumer receives the same document. It is self-describing: the labels and step names travel with the values, so the app needs no knowledge of a particular machine.

3.7 Freshness in the app

3.8 Digital twin link

The Unity twin uses the same EtherNet/IP client, on its own thread, and reads the PLC directly instead of going through the gateway. While the link is live the twin's own sequencer and manual controls are switched off, the cylinders follow the real solenoid outputs, and the workpiece is coloured once the real sensors classify it. If the link drops, the twin returns to offline simulation.

4. Proposal: a compact edge device

Today the "edge" is a Windows PC on the bench. It works, but it is large, it is someone's workstation, and it sends far more data than it needs to. A small dedicated device fixes all three. Everything in this section is a proposal; none of it is built yet.

4.1 Making the data compact

The gateway currently sends the whole self-describing snapshot every time: about 5 KB, of which almost all is labels, step names and the event log that did not change. Four steps shrink it.

  1. Send the description once. Labels, step names and fault texts are static. Publish the profile when it changes and refer to it by version afterwards.
  2. Report by exception. Send a value only when it changes, plus a heartbeat so the cloud knows the device is alive.
  3. Pack the bits. Kit 1's 22 inputs and outputs fit in 3 bytes. With step, fault, material, three counters and a timestamp, a full state frame is 17 bytes.
  4. Batch and compress when the link is poor. Group several frames into one message.

The daily figures count payload only, without protocol overhead, and assume the machine changes state at the maximum publish rate all day, which is a ceiling. The point is the ratio: about 290 times less data, which is the difference between needing a wired connection and running comfortably on a cellular modem.

A single-board industrial computer in the Raspberry Pi Compute Module class is the smallest that fits; a commercial industrial gateway fits where certified hardware is required. The gateway's resource use on such hardware has not been measured.

Unchanged by design. The edge device still only reads. The machine network port never carries traffic from the plant network or the internet, and the device still only opens outbound connections.

5.5 Security position

QuestionAnswer today
Can this system start, stop or change my machine?No. It implements reading only, at the protocol level and at the web API.
Does it open my plant network to the internet?No. The gateway makes outbound HTTPS connections only.
Who can send data as my machine?Only a holder of that machine's token. The cloud stores the token's hash, not the token.
Who can view my machine's state?Gap Anyone who has the dashboard address. There is no sign-in yet.
Is history kept?Gap No. Only the latest state is stored; the event log lives in the gateway's memory and resets when it restarts.
What happens if the internet drops?Gap Readings in that period are not sent later. The local page keeps working.
