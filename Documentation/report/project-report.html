Project report · 18 November 2026

Digital twin and remote monitor for a pneumatic training rig

A Gravitaz MATK-R5M pneumatic trainer, driven by an Allen-Bradley Micro850 PLC, was brought to life in three linked forms: the real machine, a Unity digital twin that mirrors it, and a web dashboard that shows its state from anywhere. This report describes what was built, how it fits together, what was measured, and what is still open.

1. Summary

The trainer has one PLC and interchangeable mechanical kits. Each kit is a small machine: it feeds workpieces from a magazine, tells them apart, and sorts or assembles them with pneumatic cylinders. The project set out to make Kit 1 run on the real hardware, connect it to its digital twin, and then extend the same approach to the other kits.

  • Kit 1 works end to end. The real machine sorts metal from plastic, and the Unity twin follows it live by reading the PLC over the Ethernet cable.
  • Kit 3 runs on the rig with one open fault. Its program feeds, stamps, picks a part up by vacuum and sorts it into two trays, but the arm does not lift after the grip while the head is extended.
  • A remote dashboard is live. A read-only gateway on the rig PC publishes the machine state to a cloud relay, and a React Native app shows a factory-floor view and a page per station.
  • All five kits have real CAD models in the app. Kits 2, 4 and 5 have no PLC program yet, so they run as simulations only.

2. System architecture

Everything hangs off one Ethernet cable between the rig PC and the PLC. Three programs read the controller through it at the same time, and none of them can change it. From the rig PC the state travels outwards only: the PC opens the connection to the cloud, so nothing on the lab network is exposed to the internet.

Why a gateway and a relay

The PLC gives itself a new link-local address from time to time and is only reachable from the PC plugged into it. The gateway hides that: it finds the controller with an EtherNet/IP broadcast, works out which kit program is loaded by probing for that kit's variables, and turns about forty raw values into one snapshot with the step name, fault text, cycle time and an event log. The relay is one database row per machine. The gateway writes it with a per-machine token; the app reads it with a public key and receives changes as they happen.

If readings stop arriving, the app marks values as "last known" and then hides them. It never shows an old value as if it were live.

3. Kit 1: metal and plastic sorting

Cylinder 1A pushes the bottom part from the magazine onto a raised lift. Two sensors look at it: the inductive one sees only metal, the capacitive one sees any part. Plastic is pushed off at the upper level into Tray 2. For metal the lift goes down, the lower ejector pushes it into Tray 1, and the lift comes back up.

What bring-up taught us

  • The outputs need their own supply lead. The PLC's output lights came on but no cylinder moved until a lead joined a 24V jack to the 24VDC jack of the output block.
  • The wiring sheet had the reed switches the wrong way round. DI-0 is "pulled in", not "pushed out". Directions were checked at the rig, not taken from the sheet.
  • A part that stops beside the sensor is not seen. Plastic parts gave fault 4 until the feed position was adjusted mechanically.
  • The valves hold their last position. The E-stop stops new moves but does not pull cylinders back or cut the air.

4. Kit 3: stamping and vacuum pick and place

Kit 3 has only two position switches (both on the feed cylinder), so every other move is timed. A camera classifies the part, it is stamped, and an arm with a vacuum cup picks it up. Plastic is dropped straight into Tray 1; for metal the arm turns a quarter turn to Tray 2 first.

Open problem. After the grip the PLC switches the arm-up coil on, but the arm stays down until the head has pulled in. It behaves the same with the vacuum lead unplugged, so the vacuum is not starving the lift. Still to check: lifting the arm by hand with the head out and the air off, and the flow-control screws on cylinder 4A.

How the coil pairing was settled

Cylinders 3A and 4A have no sensors, so the PLC cannot say which coil moved which cylinder. Two attempts to fix the order by re-pairing coils made things worse. A read-only recorder then logged every output during one cycle, which showed that DO-4/DO-5 are the two coils of one valve and DO-6/DO-7 of the other. Pairing them any other way puts both coils of one valve on together, so nothing moves in one step and two things move in the next. The lesson recorded in the notes: measure before changing the program.

5. The dashboard

The dashboard is written once in React Native and runs in a browser today; the same code can be built for Android and iOS. Its visual style follows high-performance HMI practice (ISA-101): a calm, low-contrast surface where normal operation is shown in ink and one data colour, and strong colour is kept for faults and lost data.

On 18 November the hosted app reported a real fault from the rig: "Fault 9, homing did not finish". The live inputs showed 1A and 3A reporting "pulled in" but not 2A, which pointed straight at the 2A reed switch or its lead. That is the kind of remote diagnosis the dashboard is for.

6. Getting the CAD into a browser

The 3D view uses each kit's own CAD model, not a drawing of it. The files were far too large for a phone, and two of the kits arrived in a form where nothing could move on its own.

Separating the piston from the cylinder

Kits 4 and 5 exist only as Solid Edge IGES exports. A standard CAD reader returns each kit as one fused shape, so a cylinder could only move as a whole, and in an earlier attempt it was the nut on the rod that moved while the rod stayed put. The IGES file does record which faces belong to which part, so a converter was written to recover that structure.

For Kits 1 to 3 the motion rules were taken from the existing Unity scripts: which components move together, how far, and in which direction. One detail mattered: Unity mirrors the X axis when it imports these files, so a "right" in a Unity script is "left" in the CAD.

8. Safety and access

  • Nothing built here can write to the PLC. The EtherNet/IP client implements only "read tag", and the gateway refuses every HTTP method except GET. Only CCW, used by a person at the PC, changes the program.
  • The lab network is not exposed. The rig PC makes outbound connections only.
  • The relay accepts data only with a per-machine token, stored as a hash. A wrong token is rejected, and the token table cannot be read through the public key.
  • The dashboard address is public and has no sign-in. Anyone with the link can read the machine state. Sign-in should come before the link is shared widely, and before any command feature is added.
